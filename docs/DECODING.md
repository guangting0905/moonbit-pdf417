# 解码链路

本文逐步说明 `decode_matrix` 做了什么，以及每一步**为什么必须在这个位置**。
解码比编码更容易写错，因为错了往往不是报错，而是给出一个看起来正常的错误答案。

---

## 输入约定

解码器的输入是**逻辑模块矩阵**：每个模块一个布尔值，一行一个符号行，
不含缩放、不含静区。这正好是 `Symbol::matrix()` 给出的形状，
也是 CLI 里 `--format text` 输出的 `#`/`.` 网格。

**为什么不是图片**：从照片里找到条码、二值化、纠正倾斜与透视，是扫描器的问题，
不是条码编解码器的问题。把两者混在一起，会让「本项目到底保证了什么」变得模糊。
`docs/DECODING.md` 只讲码字层。

---

## 第 0 步：由矩阵尺寸推出几何

```text
width == 17 * columns + 69     ->  columns = (width - 69) / 17
height                          ->  rows
```

`17 * columns + 69` 的来历：起始图案 17 + 左侧行指示符 17 + `columns × 17`
+ 右侧行指示符 17 + 终止图案 18 = `17 * columns + 69`。

不满足这个整除关系、列数超出 1..30、行数不在 3..90，都直接抛
`DecodeFailed`——**这些是标准的硬约束，不是本实现的限制**，所以拒绝比猜测正确。

---

## 第 1 步：读取行指示符（多数表决）

每一行的左、右两个行指示符各承载一个几何量，具体是哪一个由该行的簇号决定
（簇号 = 行号 mod 3）：

| 簇 | 左指示符 | 右指示符 |
| --- | --- | --- |
| 0 | `(rows − 1) / 3` | `columns − 1` |
| 1 | `3·ec + (rows − 1) mod 3` | `(rows − 1) / 3` |
| 2 | `columns − 1` | `3·ec + (rows − 1) mod 3` |

实际值还要加上 `30 · (row / 3)`，所以取模 30 就还原出上面那个量。

**关键设计：对全部行做多数表决，而不是取第一个能读的。** 一行被打坏时，它
仍然可能精确匹配到**另一个合法图案**，给出一个看似正常的错值。因为几何信息在
每一行都重复，多数值才是证据：

```moonbit
let rows_votes : Array[Int] = Array::make(30, 0)   // 三个量都 < 30
// 逐行读取；只有精确匹配才计票
let rows_x = winner(rows_votes)
```

只有**精确匹配**才投票。近似匹配说明该符号字符已经损坏，那是噪声不是信息。

由此得到 `rows = 3 · rows_x + (ec_x mod 3) + 1`、
`columns = columns_x + 1`、`ec_level = ec_x / 3`。

若三个量一个都取不到，解码器**直接失败**，不去猜纠错级别——纠错块大小猜错，
后面所有纠错都是错的，而报「读不出」远比报一个错答案安全。

---

## 第 2 步：读出全部符号字符

每一行按 `起始(17) | 左指示符(17) | columns × 数据(17) | 右指示符(17) | 终止(18)`
切片，每个 17 模块的片段在**该行簇**对应的图案表里查表。

- 精确命中 → 得码字；
- 没有命中 → 取 17 位汉明距离最近的图案，并把 `unmatched_characters` 加一。

这两个计数必须分开，因为它们描述的是不同的事：

- **整字符被替换**（相当于打印机错位）→ 图案仍然精确匹配，`unmatched` 为 0，
  但码字是错的，只有 Reed-Solomon 能发现；
- **位级划伤** → 图案不在表里，`unmatched` 增加；若它恰好离原图案最近，
  最近邻就会把码字「吸」回正确的值，此时 `corrected` 反而是 0。

---

## 第 3 步：Reed-Solomon 纠错

块长 `n = rows × columns`，纠错码字数 `2^(level+1)`，最多修正其一半个错误。

1. **伴随式** `S_i = c(3^i)`，`i = 1..2t`。全零就是合法码字，直接返回 0。
2. **Berlekamp-Massey** 解关键方程，得到错误定位多项式
   `σ(x) = ∏(1 − X_k x)`（升幂表示）。
3. **Chien 搜索**：对每个位置 `j`，令 `X = 3^(n−1−j)`，检查 `σ(X^-1)` 是否为 0。
4. **Forney**：`magnitude = X · Ω(X^-1) / σ'(X^-1)`，其中
   `Ω(x) = S(x)σ(x) mod x^(2t)`。
   注意 `magnitude` 等于**负的**错误量级，所以修复是 `words[j] += magnitude`。
5. 改完之后**重新算一遍伴随式**；还有非零就抛错，绝不接受。

三个容易写错的地方，都在这里：

- **求值方向**：`σ` 与 `Ω` 是升幂的，要用 `poly_eval_asc`，不能用码字块那套降幂的。
- **`Ω` 的截断**：必须恰好保留 `2t` 项。多留一项时，它在错误定位点处
  正好抵消掉主系数，算出来的量级是 0——现象是「纠错静默地什么都不修」。
- **符号**：Forney 给的是负量级，写成减法就把好块改坏。

---

## 第 4 步：读长度描述符（必须在纠错之后）

第一个码字是长度描述符，等于 `数据 + 填充 + 1`，**不含纠错码字**。
由于

```text
符号字符总数 = 长度描述符 + 纠错码字数
```

所以几何一旦确定，长度描述符就被唯一确定了。于是：

```moonbit
let length_descriptor = codewords.length() - ec_count
if codewords[0] != length_descriptor { raise ... }   // 两种独立来源互相校验
```

**顺序不能反。** 先读描述符再纠错在干净符号上完全正确，只有描述符本身被打坏时
才暴露，而且暴露得很脏：所有错误都修好了，载荷却被截断。这是本项目开发中
被错误注入测试抓出来的真 bug，回归测试在 `decode_test.mbt`。

---

## 第 5 步：逆压缩

只对数据区（`codewords[1..length_descriptor)`）做，填充与纠错码字不参与。
按顺序遇到锁存码就切模式：

| 码字 | 含义 |
| --- | --- |
| 900 | 切到文本压缩（同时是填充码字） |
| 901 | 切到字节压缩，段长不是 6 的倍数 |
| 924 | 切到字节压缩，段长是 6 的倍数 |
| 902 | 切到数字压缩 |
| 913 | 移入一个字节，之后回到文本模式 |

### 文本段

每个码字是 `30·a + b`，展开成两个 base-30 值，走子模式状态机：
`UPPER` / `LOWER` / `MIXED` / `PUNCT`，配 latch 与 shift。
文本压缩从 `UPPER` 开始——这也是**行首文本段不带锁存码**的原因。
末尾单字符用 29 补齐，29 在四个子模式里都是切换码，不承载数据，所以自然被忽略。

### 字节段

**段的终点是第一个 ≥ 900 的码字。** 这条规则同时解释了填充：填充码字 900
本身就落在段尾，会终止该段而不会被当成数据。

段内规则：

```text
累加最多 5 个码字，遇到 ≥ 900 就停
若恰好 5 个 且（本段用 924 或 后面还有 < 900 的码字）
    -> 5 个码字转 6 个字节
否则
    -> 回退，把这几个码字按字面字节读
```

累加器必须是 `Int64`：`900^5 ≈ 5.9e14`，6 个字节需要 48 位。

### 数字段

段内全是 < 900 的码字，从前往后每 15 个切一组。
之所以能这样切：一个完整分组是 44 位数字，加上保护前导零的前导 `1` 就成 45 位数，
而 `10^44 ≤ 值 < 900^15`，所以**恰好 15 个码字，不多不少**。
只有最后一组可能不足 15 个，而它后面不会再有分组。

每组还原成十进制字符串后，首字符必须是 `1`（那个前导标记），去掉它，
剩下的就是原始数字——包括原本的前导零。

---

## 第 6 步：字节 → 文本

`Decoded::bytes()` 给原始字节，`Decoded::payload()` 尝试 UTF-8 解码成字符串；
解码失败时退回十六进制表示，而不是报错丢弃——二进制载荷是合法输入。

---

## 报告字段怎么用

`DecodeReport` 把「发生了什么」摊开，而不是只给一个成功／失败：

| 字段 | 含义 | 典型用途 |
| --- | --- | --- |
| `unmatched_characters` | 图案未能精确匹配的符号字符数 | 判断符号的物理损伤程度 |
| `corrected_errors` | Reed-Solomon 实际修正的码字数 | 判断纠错余量还剩多少 |
| `indicator_rows/columns/ec_level` | 从行指示符独立读出的几何 | 与矩阵尺寸交叉校验 |
| `length_descriptor` | 纠错后确认的长度描述符 | 与几何推算值互相印证 |

**`unmatched` 与 `corrected` 不是同一件事的两个名字**，把它们合起来会丢掉
「损伤有多严重」这个信息。接近纠错容量上限的符号应当被识别出来并重印，
而不是等到读不出才发现。
