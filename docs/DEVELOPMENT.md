# 开发历程

这份文件记录项目是怎么长出来的：选型的依据、走过的弯路、被自己的测试抓出来的
bug，以及刻意留下的边界。写给下一个接手的人（可能是人类，也可能是 AI）。

---

## 一、为什么是 PDF417

### 从「生态里缺什么」倒推选题

选题不是拍脑袋定的。做法是先把 mooncakes.io 上的包按 300 多个关键词扫一遍，
看哪些方向已经被占满：

| 方向 | 检索结果 |
| --- | --- |
| TOML / YAML / INI / CSV / JSONPath 解析 | 各有 7～20 个实现 |
| cron 表达式 | 至少 7 个 |
| 文本 diff / patch | 至少 6 个 |
| Unicode 宽度／字素／规范化／双向文字 | 各有 5～20 个 |
| DEFLATE / gzip / zlib | 至少 8 个（含 `moonbit-community/flate` 这类高质量实现） |
| QR 码 | 至少 5 个 |
| 一维条码 | 2 个成熟的（覆盖 EAN/UPC/Code 39/93/128/ITF-14） |
| **PDF417 / DataMatrix / 2d barcode / iso15438** | **全部 0 个** |

结论很清楚：**二维条码里的 PDF417 是空白**。而且它不是一个玩具——它有明确的
规范（ISO/IEC 15438）、真实的使用场景（身份证、机票、物流面单、票据）、
以及一个「做对了可验证、做错了会静默出错」的工程内核。

### 为什么不是更简单的东西

QR 码已经被做过 5 次，再做一个只能比谁写得短；一维条码有人做到了工业级覆盖。
PDF417 的价值在于**它有一条完整的、可以逐层验证的链路**：

```text
字节 → 分段压缩 → 码字 → Reed-Solomon → 布局与行指示符 → 17 位图案 → 模块网格
```

每一层都能被独立检验，而且有一条现成的、被大量生产系统使用的解码器可以反向
验证整条链路——这比「再实现一个解析器」有意思得多。

## 二、验证策略：先想清楚「拿什么证明它对」

### 三个外部锚点

动手之前先确认了三件事能不能做，因为**不能验证的功能等于没做**：

| 锚点 | 用途 | 结论 |
| --- | --- | --- |
| `pdf417gen`（PyPI，纯 Python） | 独立生成一致性向量：码字流 + 模块网格摘要 | 可用 |
| `zxing-cpp`（PyPI 轮子） | 真实解码器读回本项目生成的位图 | 可用 |
| ISO/IEC 15438 的纠错系数表 | 核对**推导出来**的生成多项式系数 | 可用（经 pdf417gen 转写） |

选择 `pdf417gen` 而不是 zxing 的 Java 实现，是因为它是纯 Python、可直接读取
内部数据结构，能把「码字流」这一层单独导出来对照——这一层比最终位图更能定位
问题出在哪一步。

### 一个刻意的决定：纠错系数不抄表

标准给出的是每个级别的系数表（总共 1022 项）。直接抄表是最快的，
但那样「系数对不对」就变成了「抄得准不准」。

本项目改成现算：`g(x) = ∏(x − 3^i) mod 929`，再拿标准表**核对**计算结果。
于是 1022 项系数一致就成了一个有意义的结论，而不是抄写练习。
验证脚本第一次跑就 9 个级别全对，这本身也说明推导路径是对的。

### 一个刻意的决定：图案表只能当数据

符号字符图案表（929 个值 × 3 个簇）是标准里的**规范性数据表**，没有公开的
闭式生成规则，所以它必须是数据。

既然必须是数据，就给它配上**结构自检**：17 模块、4 条 4 空、每段 1～6 模块、
以条开始以空结束、簇号满足 `(b1 − b2 + b3 − b4) mod 9`、同簇内 929 个图案互不重复。
2787 条全部通过。这样「数据对不对」至少有了一个不依赖外部对照的检查。

## 三、被自己的测试抓出来的两个静默 bug

这两个 bug 都不会让程序崩溃，只会让结果错——正是这类 bug 让「先写验证」变得值得。

### bug 1：长度描述符读在纠错之前

**现象**：错误注入测试里出现「载荷只有前半段，但报告说错误已全部修正（`corrected=4`）」。

**根因**：`decode_matrix` 先读 `codewords[0]` 得到数据区长度，再跑纠错。
注入的位置恰好包含 `codewords[0]` 时，解码器读到的是**损坏后的**长度，
于是只解了一部分数据；而 Reed-Solomon 随后把码字全部修好了，
报告如实说「修了 4 个错误」。

这个 bug 的欺骗性在于**报告是对的，行为是错的**。

**修复**：顺序反过来——先由行指示符拿到纠错级别 → 纠错 → 再读长度描述符。
顺带发现一个更强的校验：既然 `符号字符总数 = 长度描述符 + 纠错码字数`，
那么长度描述符由几何**唯一确定**，可以拿存储值和推算值互相印证，
不一致就说明块没真修好。

**回归测试**：`decode/damaging the length descriptor does not truncate the payload`。

### bug 2：字节压缩解码用了 32 位累加器

**现象**：某些纯字节载荷解出来**长度对、内容从第 7 个字节起整体偏移**。

**根因**：解码字节压缩段时用 `value = 900 * value + codeword` 累加 5 个码字，
最大 `900^5 ≈ 5.9e14`，远超 32 位。MoonBit 的 `Int` 是 32 位，于是静默回绕。

有意思的是**编码侧没有这个问题**：那边是逐位长除法，每一步的中间量都小于
`900 × 256`。同一件事的两种写法，只有一种会溢出。

**修复**：解码侧改用 `Int64`。并补了一条测试专门压这个场景，
注释里写明「48 位累加器正是 32 位会静默回绕的地方」。

### bug 3：Forney 公式与 Ω 截断（在标定阶段就暴露了）

纠错写完后，单码字错误测试直接失败。排查过程：

1. 先在 Python 里把整套公式**镜像实现**一遍，确认 `S_i = e · X^i` 成立；
2. 发现镜像里 Chien 搜索找不到根——**多项式求值方向反了**：
   码字块是降幂书写，而 `σ`、`Ω` 是升幂，用了同一个 Horner；
3. 改对方向后仍有失败——**`Ω(x)` 的截断多留了一项**：它恰好抵消主系数，
   使算出的错误量级变成 0；
4. 再改对之后，48 组（位置 × 量级）全过。

**教训**：这三个错误都不会崩，只会算错，而且中间状态看起来都「挺合理」。
正确的做法是先在一个可以逐步打印的 Python 镜像里把符号约定钉死，
再把这套约定原样搬进 MoonBit——`docs/DECODING.md` 里那一节就是这次标定的产物。

### bug 4：行指示符取第一个可读值

错误注入把某一行的两个行指示符换成了**另一个合法图案**——图案仍然精确匹配，
于是「取第一个能读到的」策略会得到一个看起来正常的错值（行的 `rows_x` 变成 20，
推出 62 行）。

**修复**：改成对全部行多数表决，只让精确匹配投票。
这既修掉了问题，也把「行指示符为什么要每行重复」这个设计意图落实进了代码。

## 四、刻意留下的边界

下面这些是**主动决定不做**的，不是没来得及做：

1. **不做图像识别。** 解码器只吃逻辑模块矩阵。加进二值化、透视校正会让
   「本项目保证什么」变模糊，也会引入一堆无法在本仓库验证的启发式。
2. **不做 PNG／JPEG 输出。** 输出 PBM 之后一行 shell 就能接上图像工具链；
   在条码库里内置一个位图编码器只会扩大维护面。
3. **不做「尽量猜」式纠错。** 超出容量就报错。对条码而言，猜错的代价高于读不出。
4. **不做数据区之外的容错。** 行指示符读不到就失败，不尝试枚举 9 个纠错级别。
   猜错级别会让后面所有纠错都作用在错误的块上。

## 五、AI 在其中做了什么

- **调研与选题**：生态扫描（300+ 关键词）、参考实现选型、验证路径设计。
- **实现**：全部 MoonBit 代码、生成脚本、验证脚本、文档初稿。
- **调试**：上面四个 bug 的定位过程基本是「先写一个能逐步打印的等价实现，
  把约定钉死，再搬回来」。
- **人类负责的部分**：判断选题价值、决定边界（不做图像识别、不做 PNG）、
  判断哪个 bug 值得写进文档、以及所有对外发布动作。

需要说明的是：**提交进仓库的每个数字都用命令行重新跑过一遍**，
README 里没有未经实测的陈述。这一条在本项目的语境下不是客套——
开源赛事的评审明确说过，过度声明会被直接驳回。
